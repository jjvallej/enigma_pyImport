# Flujo detallado de DAGs - Fuente Evaplan

Este flujo se ejecuta con tres DAGs: `src_planeacion_ingest_evaplan`, `src_planeacion_load_evaplan` y `src_planeacion_transform_evaplan`. El orden operativo es ingesta, luego carga y finalmente transformación; además, `ingest` dispara `load` y `load` dispara `transform`, por lo que la cadena queda automatizada.

La ejecución inicia en `dags_evaplan/src_evaplan_ingest_dag.py`. Este DAG autentica contra la API de Evaplan usando configuración de `config/config.yaml` en `evaplan.auth_endpoint`, `evaplan.api_base_url`, `evaplan.credentials` y `evaplan.endpoints`. Después consulta periodos, guarda periodos en GCS, vuelve a leerlos desde GCS y procesa todos los `peri_idp` encontrados. Para cada periodo consume los endpoints `avance_mr`, `avance_mp`, `avance_x_subprograma`, `avance_general`, `avance_subprogramas`, `avance_programas` y `sector_mp`. Cada respuesta JSON se guarda en el bucket `DEFAULT_BUCKET_NAME` dentro de `evaplan.gcs_base_folder` y subcarpetas de `evaplan.gcs_folders.*`. Al terminar, lanza `src_planeacion_load_evaplan`.

La carga está en `dags_evaplan/src_evaplan_load_dag.py` y usa `DATASET_ID_BRONZE`, `DEFAULT_BUCKET_NAME`, `CONF.evaplan.fuentes` y los nombres de tablas en `CONF.evaplan.tables.bronze`. Primero asegura el dataset bronze con `ensure_dataset()` de `modules/evaplan/evaplan_load.py`. Luego, para cada fuente, ejecuta `load_json_files_to_bq()`: busca solo JSON de la fecha actual, combina registros de todos los JSON del día, agrega `fecha_lectura` y `peri_idp`, elimina posibles duplicados del mismo día/período en la tabla destino y carga en BigQuery con la tabla `evaplan_api_{fuente}_raw_data` (según mapeo de config). Al finalizar dispara `src_planeacion_transform_evaplan`.

La transformación está en `dags_evaplan/src_evaplan_transform_dag.py`. Este DAG usa `DATASET_ID_SILVER`, `DATASET_ID_GOLD` y `get_dbt_command()` de `modules/config.py`, además de utilidades de `modules/evaplan/evaplan_transform.py`. Primero obtiene `peri_idp` únicos desde bronze de la fecha actual (`get_all_peri_idps_from_bronze`). Luego transforma cada fuente de bronze a silver con `transform_fuente_to_silver()`, eliminando en silver los periodos que se van a recargar y copiando el dato actualizado. Después ejecuta modelos dbt en gold para las tablas processed (`evaplan_api_avance_*_processed_data` y `evaplan_api_sector_mp_processed_data`) y finalmente ejecuta modelos dbt de facts (`evaplan_api_processed_data_fact_entidad`, `..._fact_programa`, `..._fact_resumen`, `..._fact_sector`) que generan `FACT_ENTIDAD`, `FACT_PROGRAMA`, `FACT_RESUMEN` y `FACT_SECTOR`.

Durante los comandos dbt, `get_dbt_command()` exporta `DBT_PROJECT_ID`, `DBT_DATASET_BRONZE`, `DBT_DATASET_SILVER`, `DBT_DATASET_GOLD` y `DBT_LOCATION`, e inyecta `--vars` con `project_id`, `bronze_dataset`, `bronze_seguridad_dataset`, `silver_dataset` y `gold_dataset`. En este DAG también se inyectan variables de nombre de tabla de Evaplan para gold y facts (por ejemplo `evaplan_gold_avance_mr_table_name`, `evaplan_gold_fact_entidad_table_name`) tomando valores desde `CONF.evaplan.tables.gold` y `CONF.evaplan.tables.gold_facts`.

Lo parametrizable en `config/config.yaml` para esta fuente está en `evaplan`: `auth_endpoint`, `api_base_url`, `endpoints.*`, `gcs_base_folder`, `gcs_folders.*`, `fuentes`, `tables.bronze.*`, `tables.silver.*`, `tables.gold.*`, `tables.gold_facts.*` y `credentials.usuario/password`. También es parametrizable por ambiente en `environments.<env>`: `project_id`, `location`, `bucket_name`, `dataset_bronze`, `dataset_silver` y `dataset_gold`.

## Explicación simple (modo no técnico)

Este flujo funciona como una cadena en tres pasos. Primero, un DAG se conecta a la API de Evaplan, pide la información por periodos y guarda los resultados en archivos JSON dentro de Cloud Storage, separados por tipo de endpoint. Segundo, otro DAG toma esos JSON del día, los organiza y los carga en tablas base de BigQuery (capa bronze), dejando la información lista para transformar.

Tercero, el DAG de transformación toma esas tablas base y actualiza la capa silver y luego la capa gold, donde se crean tablas finales de consulta y tablas FACT para análisis de negocio. En resumen, el camino es: API Evaplan -> JSON en Cloud Storage -> tablas base en BigQuery -> tablas finales y facts para reportes.

Si cambian endpoints, rutas de almacenamiento, nombres de tablas o credenciales, esos cambios se hacen en `config/config.yaml` sin rehacer toda la lógica del flujo.
